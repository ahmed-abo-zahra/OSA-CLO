# ASO CLO — متجر إلكتروني ولوحة شركاء

تطبيق Full Stack لمتجر متعدد الشركاء، بواجهة عربية/إنجليزية ولوحة إدارة للشركاء وواجهات REST API وقاعدة PostgreSQL على Supabase. التطبيق الرئيسي مبني بـReact وNext.js ويستخدم Route Handlers على Node.js. مجلد `frontend-demo/` عرض HTML ثابت منفصل ولا يمثل التطبيق الكامل.

## الروابط

- **التطبيق الرئيسي:** https://aso-clo-platform.vercel.app
- **العرض الثابت للواجهة:** https://aso-clo-frontend-demo.vercel.app
- **مستودع GitHub:** https://github.com/ahmed-abo-zahra/OSA-CLO

> رابط العرض الثابت يستخدم محتوى توضيحيًا للواجهة فقط. التطبيق الرئيسي هو مشروع Full Stack. لا يوجد دفع إلكتروني؛ الطلبات المسجلة غير مدفوعة.

## التقنية والمعمارية

| الطبقة | التقنية |
|---|---|
| الواجهة | React 19، Next.js App Router، TypeScript، Tailwind CSS |
| Backend | Node.js عبر Next.js Route Handlers |
| REST API | مسارات عامة للكتالوج والتقييمات والتتبع، ومسارات إدارة محمية |
| قاعدة البيانات | Supabase PostgreSQL مع migrations محفوظة في المستودع |
| الصور | صور كتالوج توضيحي في `public/catalog/`، وصور المنتجات المضافة من لوحة الشركاء في Supabase Storage |
| مصادقة الإدارة | كلمات مرور الشركاء في متغيرات الخادم وجلسات HMAC موقعة داخل cookie من نوع HttpOnly تنتهي بعد 12 ساعة |
| النشر | Vercel للتطبيق الرئيسي؛ `frontend-demo/` مستقل عنه |

مسار Checkout يستقبل معرّفات المنتجات فقط، ويستنتج ملكية الشريك من قاعدة البيانات على الخادم؛ ثم يتحقق من الأسعار والخيارات والخصومات والمخزون داخل PostgreSQL وينشئ الطلبات ويخصم المخزون ضمن معاملة ذرية. عند اشتمال السلة على منتجات من أكثر من شريك، يُنشأ طلب لكل شريك. إنشاء الطلب اليدوي وتحديثه من لوحة الإدارة يستخدمان معاملات/دوال قاعدة بيانات مناسبة لتقليل حالات السباق.

المفتاح `SUPABASE_SECRET_KEY` خادمي فقط. الوصول العام إلى جدول المنتجات محدود بسياسات RLS وصلاحيات الأعمدة. ويعيد `GET /api/products` قائمة حقول عامة محددة فقط؛ لا يعيد سعر التكلفة أو معرّف الشريك أو بيانات الإدارة. عمليات التغيير تتحقق من المصدر same-origin، والعمليات العامة ذات الأثر تخضع لتحديد معدل محفوظ في PostgreSQL. واجهة المتجر تقرأ من REST ولا تشترك في بث Realtime لصفوف المنتجات.

## كتالوج المنتجات وبيانات العملاء

يحافظ التطبيق الحي على **120 منتجًا توضيحيًا مع صورها** كي يظل المتجر معبأً وقابلًا للتقييم والتصفح. المنتجات وأسعارها ومخزونها وصورها في migrations و`public/catalog/` هي بيانات Portfolio/عرض وليست إقرارًا بمخزون تجاري حقيقي. لا تحذف كتالوج المنتجات أو صوره ضمن تنظيف بيانات العملاء؛ يجب أن تبقى روابط الصور والمنتجات شغالة في Production. وتعرض واجهة المتجر المنتجات المحفوظة فعليًا؛ وإذا أصبح الكتالوج فارغًا لأي سبب، تعرض مساحة علامة محايدة بدل صور منتجات افتراضية.

لا تحتوي migrations أو fixtures المحلية على طلبات أو تقييمات عملاء وهمية. طلبات وتقييمات المتجر تُنشأ فقط عند إرسال مستخدم لها عبر الواجهات، ومراجعات المنتجات تنتظر موافقة الإدارة قبل الظهور. بيانات الطلب تتضمن معلومات العميل التي يرسلها المشتري؛ لذلك لا تستخدم بيانات أشخاص حقيقيين أثناء الاختبار، وامسح سجلات الاختبار فقط بعد التحقق من أنها سجلات تجريبية.

الملف `src/lib/demo-products.json` وصور `public/demo/` مخصصان لوضع Demo المحلي. كما أن `frontend-demo/` عرض ثابت مستقل. لا تستخدم هذه الملفات أو أي أسعار/كميات توضيحية لاتخاذ قرارات بيع حقيقية.

## الوظائف وواجهات API

- متجر عربي/إنجليزي متجاوب، بحث وفلاتر وفئات، تفاصيل منتجات وسلة.
- Checkout للضيف؛ الخادم يعيد التحقق من الأسعار والكميات والمخزون والخيارات قبل تسجيل الطلب.
- `GET /api/products` يعرض المنتجات المتاحة فقط عبر صفحات REST وحقول عامة محددة.
- `POST /api/checkout` يسجل الطلب بعد التحقق الخادمي؛ لا يجمع أموالًا ولا يتصل ببوابة دفع.
- `POST /api/discount/validate` يتحقق من كوبون الخصم والسلة؛ التحقق النهائي يُعاد داخل معاملة Checkout.
- `GET/POST /api/reviews` يعرض التقييمات المعتمدة ويستقبل تقييمات تنتظر موافقة الإدارة.
- `GET /api/track/{orderId}` يعرض حالة الطلب والإجمالي والمبلغ المدفوع واسمًا مخفيًا جزئيًا؛ لا يعيد الهاتف أو العنوان.
- `/api/admin/*` لإدارة المنتجات والطلبات والخصومات والإعدادات، مع عزل الشريك والتحقق من الجلسة.
- استيراد CSV للمنتجات يدعم حتى 100 صف في العملية ويرسل multipart إلى المسار الإداري الفعلي؛ الاستيراد ليس معاملة كلية، لذلك قد ينجح بعض الصفوف وتفشل أخرى مع عرض الأخطاء.

**لا توجد حسابات عملاء أو تسجيل دخول Google/WhatsApp في النسخة الحالية.** المشتري يستخدم Checkout كضيف، والمصادقة الموجودة مخصصة للشركاء Partner A وPartner B وPartner C. لا تظهر أزرار WhatsApp حتى يُضبط رقم عمل حقيقي ومعتمد في `NEXT_PUBLIC_WHATSAPP_NUMBER`.

## المتطلبات والتشغيل المحلي

- Node.js `>=22.13.0 <27` وnpm.
- مشروع Supabase مخصص للتطبيق عند استخدام Backend الحقيقي.

```bash
npm ci
cp .env.example .env.local
```

للتجربة المحلية المعزولة دون اتصال بـSupabase، اجعل `NEXT_PUBLIC_DEMO_MODE=true` في `.env.local` ثم شغّل:

```bash
npm run dev
```

افتح http://localhost:3000. حسابات Demo المحلية هي `Partner A` أو `Partner B` أو `Partner C`، وكلمة مرور العرض المحلي `aso-demo-2026`؛ لا تستخدمها في الإنتاج. بيانات المنتجات الاصطناعية متاحة في هذا الوضع المحلي فقط. تغييرات Demo تُحفظ تحت `.demo/` والصور في `public/demo/uploads/`؛ هذه الملفات مستثناة من Git، ووضع Demo غير مناسب لاستضافة متعددة النسخ.

## إعداد Supabase

يوضح `.env.example` أسماء المتغيرات المطلوبة. للإنتاج المحلي أو Vercel:

```dotenv
NEXT_PUBLIC_DEMO_MODE=false
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<publishable-key>
SUPABASE_SECRET_KEY=<server-only-secret-key>
ADMIN_SESSION_SECRET=<random-secret-at-least-32-characters>
ADMIN_PASSWORD_PARTNER_A=<unique-long-random-password>
ADMIN_PASSWORD_PARTNER_B=<unique-long-random-password>
ADMIN_PASSWORD_PARTNER_C=<unique-long-random-password>
# Optional: verified business contact number, digits only
NEXT_PUBLIC_WHATSAPP_NUMBER=
```

أنشئ `ADMIN_SESSION_SECRET` عشوائيًا، مثلًا باستخدام `openssl rand -base64 48`، وضع كل الأسرار في مخزن أسرار محلي أو Vercel. اجعل كلمات المرور قوية ومختلفة. لا تضف `.env.local` إلى Git، ولا تستخدم متغيرًا يبدأ بـ`NEXT_PUBLIC_` لأي مفتاح سري.

لتطبيق migrations من المستودع على مشروع Supabase المعتمد:

```bash
npx supabase login
npx supabase link --project-ref rtokjrupdvftacewvmxm
npx supabase db push
```

تشمل migrations:

1. `20261108132251_initial_schema.sql` — الجداول وRLS وStorage ودوال Checkout والطلبات.
2. `20261108132622_seed_sample_catalog.sql` — 120 منتجًا توضيحيًا وصورًا مرتبطة بها للعرض والتقييم.
3. `20261108132723_explicit_access_policies.sql` — سياسات رفض صريحة للجداول الحساسة وفهرس إضافي.
4. `20261108144451_anonymize_partner_labels.sql` — تسميات عامة للشركاء مع الحفاظ على معرّفات الملكية الثابتة.
5. `20261108153627_security_hardening.sql` — صلاحيات أعمدة المنتجات، إزالة products من publication الخاصة بـRealtime، rate limits، ودالة تحديث طلب ذرية.
6. `20261108153712_rate_limit_deny_policy.sql` — سياسة RLS رفض صريحة للوصول المباشر إلى جدول rate limits من أدوار المتصفح.

لا توجد migration لحذف المنتجات أو صور الكتالوج. قبل حذف بيانات طلب/تقييم أثناء التنظيف، تحقّق من أنها بيانات اختبار بحتة؛ لا تحذف سجلات العملاء الفعلية أو صور المنتجات.

## النشر على Vercel

اربط مستودع `ahmed-abo-zahra/OSA-CLO` بمشروع Next.js على Vercel، واستخدم فرع `main` للنشر Production. اضبط متغيرات الإنتاج الموجودة في `.env.example` مع `NEXT_PUBLIC_DEMO_MODE=false`، وتأكد من وجود متغيرات كلمات المرور الثلاثة و`ADMIN_SESSION_SECRET` دون إضافتها إلى Git. اختبر Preview أولًا، ثم تحقق بعد النشر من الصفحة الرئيسية وصور الكتالوج و`/api/products` وتسجيل الدخول الإداري ورفض طلبات الإدارة غير المصرح بها.

لا تنشر ملف `.env`، ولا تطبع المفاتيح في سجلات CI أو الطرفية، ولا تستخدم بيانات Demo المحلية في الإنتاج. لا يوجد دفع إلكتروني؛ أي طلب يبقى غير مدفوع إلى أن يُتفق على آلية حقيقية خارج التطبيق.

## حدود النسخة الحالية

- كتالوج المنتجات الـ120 وصورها محتوى Portfolio/توضيحي محفوظ عمدًا للتقييم، وليس مخزونًا تجاريًا مؤكدًا.
- لا يوجد دفع إلكتروني؛ الطلبات غير مدفوعة حتى تأكيدها خارج التطبيق.
- لا توجد حسابات للمشترين؛ Checkout متاح كضيف.
- لا تُنشأ طلبات أو تقييمات وهمية تلقائيًا؛ طلبات الاختبار يجب أن تستخدم بيانات اصطناعية وتُنظف بعد التحقق.
- لا تعتمد على قاعدة `.demo/` كقاعدة بيانات إنتاجية أو متعددة النسخ.
