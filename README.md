# ASO CLO — متجر إلكتروني ولوحة شركاء

تطبيق Full Stack لمتجر متعدد الشركاء، بواجهة عربية/إنجليزية ولوحة إدارة للشركاء وواجهات REST API وقاعدة PostgreSQL على Supabase. التطبيق الرئيسي مبني بـReact وNext.js ويستخدم Route Handlers على Node.js. مجلد `frontend-demo/` عرض HTML ثابت منفصل ولا يمثل التطبيق الكامل.

## الروابط

- **التطبيق الرئيسي:** https://aso-clo-platform.vercel.app
- **العرض الثابت للواجهة:** https://aso-clo-frontend-demo.vercel.app
- **مستودع GitHub:** https://github.com/ahmed-abo-zahra/OSA-CLO

> رابط العرض الثابت يستخدم محتوى توضيحيًا للواجهة فقط. التطبيق الرئيسي هو مشروع Full Stack. لا يوجد دفع إلكتروني؛ الطلبات المسجلة غير مدفوعة.

## التقنية والمعمارية

| الطبقة | التقنية |
|---|---|
| الواجهة | React 19، Next.js App Router، TypeScript، Tailwind CSS |
| Backend | Node.js عبر Next.js Route Handlers |
| REST API | مسارات عامة للكتالوج والتقييمات والتتبع، ومسارات إدارة محمية |
| قاعدة البيانات | Supabase PostgreSQL مع migrations محفوظة في المستودع |
| الصور | صور كتالوج توضيحي في `public/catalog/`، وصور المنتجات المضافة من لوحة الشركاء في Supabase Storage |
| مصادقة الإدارة | كلمات مرور الشركاء في متغيرات الخادم وجلسات HMAC موقعة داخل cookie من نوع HttpOnly تنتهي بعد 12 ساعة |
| حسابات العملاء | Supabase Auth بالبريد وكلمة المرور، جلسات SSR عبر cookies، تأكيد بريد واستعادة كلمة مرور |
| النشر | Vercel للتطبيق الرئيسي؛ `frontend-demo/` مستقل عنه |

مسار Checkout يستقبل معرّفات المنتجات فقط، ويستنتج ملكية الشريك من قاعدة البيانات على الخادم؛ ثم يتحقق من الأسعار والخيارات والخصومات والمخزون داخل PostgreSQL وينشئ الطلبات ويخصم المخزون ضمن معاملة ذرية. عند اشتمال السلة على منتجات من أكثر من شريك، يُنشأ طلب لكل شريك. يرسل العميل `Idempotency-Key` فريدًا لكل محاولة؛ تحفظ قاعدة البيانات نتيجة المفتاح 90 يومًا وتعيد النتيجة نفسها عند إعادة الطلب بدل إنشاء طلب أو خصم مخزون مرة أخرى. إنشاء الطلب اليدوي وتحديثه من لوحة الإدارة يستخدمان معاملات/دوال قاعدة بيانات مناسبة لتقليل حالات السباق.

المفتاح `SUPABASE_SECRET_KEY` خادمي فقط. الوصول العام إلى جدول المنتجات محدود بسياسات RLS وصلاحيات الأعمدة. ويعيد `GET /api/products` قائمة حقول عامة محددة فقط؛ لا يعيد سعر التكلفة أو معرّف الشريك أو بيانات الإدارة. عمليات التغيير تتحقق من المصدر same-origin، والعمليات العامة ذات الأثر تخضع لتحديد معدل محفوظ في PostgreSQL. واجهة المتجر تقرأ من REST ولا تشترك في بث Realtime لصفوف المنتجات.

تخضع قائمة المنتجات العامة لكاش قصير مدته 30 ثانية على خادم Next.js وطبقة CDN، مع إبطال الكاش عند تعديل المنتجات أو إنشاء طلب يخصم المخزون. ترجع الواجهة مؤشر التوفر فقط؛ لا تكشف `stock_quantity` الدقيق، وقد يتأخر مؤشر التوفر بحد أقصى فترة الكاش، بينما يعيد PostgreSQL التحقق من المخزون الحي داخل معاملة Checkout قبل قبول أي طلب. صفحات الإدارة والطلبات وCheckout وردود التتبع تستخدم `no-store` ولا تدخل في كاش مشترك.

## دراسة حالة معمارية: 3 شركاء ولوحة تحكم مشتركة

يدير **Partner A وPartner B وPartner C** المتجر من تطبيق ولوحة تحكم واحدة، لكن الجلسة الموقعة تحدد هوية الشريك النشط لكل طلب. يربط `src/lib/partners.ts` معرّف الدخول الثابت لكل شريك بمعرّف UUID المقابل في قاعدة البيانات؛ وبعد التحقق من الجلسة، تستخرج Route Handlers هذا المعرّف من الخادم. لا يعتمد النظام على `partner_id` يرسله المتصفح، ولا يعرض UUID الشريك في كتالوج REST العام.

تُحفظ ملكية المنتجات والطلبات وأكواد الخصم في عمود `partner_id`. عند فتح لوحة التحكم، يجلب الخادم المنتجات والطلبات التابعة لمعرّف الشريك الموجود في الجلسة فقط؛ وبذلك تُحسب مؤشرات المبيعات والمبالغ المحصلة والأرصدة المستحقة من مجموعة طلباته هو، لا من إجمالي المتجر. عمليات إضافة المنتج وإنشاء الطلب اليدوي وتعديل الطلب تتحقق كذلك من ملكية الشريك في الخادم وقاعدة البيانات. وتضيف دالة تحديث الطلب قفلًا على سجل الطلب وتعيد رفضه إذا لم يطابق كل من `order_id` و`partner_id` الشريكَ المصادق عليه.

نطاق الفئات مقيد أيضًا على الخادم: Partner A يدير العبايات والفساتين والإسدالات والبناطيل والتيشيرتات؛ Partner B يدير الكعوب والنعال والسنيكرز؛ وPartner C يدير الإكسسوارات وشنط البنات والأجهزة المنزلية والمكياج. تعرض نماذج المنتج وCSV فئات الشريك فقط، وتعيد Route Handlers رفضًا `403` عند محاولة إنشاء منتج أو نقل منتج إلى فئة خارجة عن نطاقه. هذا التقسيم يطابق توزيع منتجات Portfolio الحالي، ولا يعني اعتمادها كمخزون تجاري.

| الحساب | نطاق البيانات الإدارية | نافذة العروض الترويجية |
|---|---|---|
| **Partner A** | يدير منتجاته ومخزونه وطلباته وأكواد الخصم التابعة له، ويرى مؤشرات نشاطه فقط. | يقرأ الإعداد المشترك ويملك صلاحية تحديث النافذة العامة. |
| **Partner B** | يدير منتجاته ومخزونه وطلباته وأكواد الخصم التابعة له، ويرى مؤشرات نشاطه فقط. | يقرأ الإعداد المشترك، ولا يملك تغييره. |
| **Partner C** | يدير منتجاته ومخزونه وطلباته وأكواد الخصم التابعة له، ويرى مؤشرات نشاطه فقط. | يقرأ الإعداد المشترك، ولا يملك تغييره. |

الكتالوج الذي يراه العميل مشترك ويعرض منتجات الشركاء المتاحة، لكن ذلك لا يوسّع صلاحيات الإدارة: كل طلب إداري يشتق هوية الشريك من الجلسة الموقعة ويقيّد العمليات بملكيته في `partner_id`؛ لا يستطيع تغيير `partner_id` مرسل من العميل لتجاوز هذا النطاق.

إعداد نافذة العروض الترويجية مشترك على مستوى واجهة المتجر، لكن صلاحية تغييره محصورة بـPartner A: يسمح المسار `PUT /api/admin/settings` بالحفظ لهذا الشريك وحده، بينما لا تمنح بقية الحسابات هذه الصلاحية. تُتحقق الحقول والرابط والألوان والتباين قبل حفظ إعداد `promotional_popup`، ويظل عرض النافذة عامًا وفق إعداد المتجر.

في Checkout متعدد الشركاء، يرسل المتصفح معرّفات المنتجات والكمية والخيارات المطلوبة فقط. يبحث Route Handler عن مالك كل منتج في PostgreSQL ويضيف الملكية الموثقة إلى بيانات المعاملة، ويحسب HMAC لحمولة الطلب كي لا يحفظ بيانات العميل نصيًا ضمن سجل منع التكرار. يستدعي الـhandler الدالة `public.place_storefront_order_idempotent`، التي تقفل سجل `Idempotency-Key` وتتحقق من تطابق بصمة الطلب؛ ثم تستدعي `public.place_storefront_order` الفعلية داخل المعاملة نفسها. **اسم الدالة الأساسية هو `place_storefront_order` وليس `create_checkout_order`؛ أما نقطة الدخول الحية فتضيف إليها حماية منع التكرار.** تقفل الدالة الأساسية صفوف المنتجات بترتيب ثابت لتقليل التنافس على المخزون، وتعيد التحقق من توافر المنتج والكمية والمقاس واللون والملكية، ثم تقرأ سعر البيع من قاعدة البيانات بدل الوثوق بسعر العميل.

بعد إعادة التحقق، تجمع الدالة السلة حسب `partner_id` وتنشئ طلبًا مستقلًا لكل شريك مع عناصره وإجماليه وخصمه. تتحقق من صلاحية الكوبون وتاريخ انتهائه وحد الاستخدام والحد الأدنى؛ ويُطبق الكوبون المقيد بشريك على منتجات ذلك الشريك، أما الخصم العام فيُوزع تناسبيًا على إجماليات الشركاء مع تسوية فرق التقريب في المجموعة الأخيرة. تُحدّث الدالة المخزون وعدّاد استخدام الكوبون ضمن المعاملة نفسها. لذلك إما أن تكتمل الطلبات المنقسمة وتحديثات المخزون والخصم كلها، أو يفشل الاستدعاء ويُلغى كله دون ترك نصف عملية. وعلى إعادة المحاولة بالمفتاح نفسه تُعاد الاستجابة المحفوظة دون خصم إضافي. لا يجمع هذا التدفق أي دفعة إلكترونية؛ الطلبات تبقى غير مدفوعة حتى التحصيل خارج التطبيق.

تُحدّث حالة الطلب عبر `public.update_partner_order_audited` بعد قفل سجل الطلب والتحقق من `order_id` و`partner_id`. تمنع الدالة القفز بين حالات سير العمل، وتسجل من غيّر الحالة ومتى، وتسجل تعديل المبلغ السابق والجديد وسبب التسوية في `activity_log`. خفض مبلغ محصل يتطلب سببًا واضحًا؛ ولا يقبل إلغاء طلب عليه مبلغ مدفوع ما زال مسجلًا. لإلغاء طلب غير مدفوع، تعيد الدالة مخزون عناصره داخل المعاملة نفسها؛ أما معالجة رد الأموال فتظل خارج النظام ويجب توثيق التسوية قبل الإلغاء.

## كتالوج المنتجات وبيانات العملاء

يحافظ التطبيق الحي على **120 منتجًا توضيحيًا مع صورها** كي يظل المتجر معبأً وقابلًا للتقييم والتصفح. المنتجات وأسعارها ومخزونها وصورها في migrations و`public/catalog/` هي بيانات Portfolio/عرض وليست إقرارًا بمخزون تجاري حقيقي. لا تحذف كتالوج المنتجات أو صوره ضمن تنظيف بيانات العملاء؛ يجب أن تبقى روابط الصور والمنتجات شغالة في Production. وتعرض واجهة المتجر المنتجات المحفوظة فعليًا؛ وإذا أصبح الكتالوج فارغًا لأي سبب، تعرض مساحة علامة محايدة بدل صور منتجات افتراضية.

لا تحتوي migrations أو fixtures المحلية على طلبات أو تقييمات عملاء وهمية. طلبات وتقييمات المتجر تُنشأ فقط عند إرسال مستخدم لها عبر الواجهات، ومراجعات المنتجات تنتظر موافقة الإدارة قبل الظهور. بيانات الطلب تتضمن معلومات العميل التي يرسلها المشتري؛ لذلك لا تستخدم بيانات أشخاص حقيقيين أثناء الاختبار، وامسح سجلات الاختبار فقط بعد التحقق من أنها سجلات تجريبية.

الملف `src/lib/demo-products.json` وصور `public/demo/` مخصصان لوضع Demo المحلي. كما أن `frontend-demo/` عرض ثابت مستقل. لا تستخدم هذه الملفات أو أي أسعار/كميات توضيحية لاتخاذ قرارات بيع حقيقية.

## الوظائف وواجهات API

- متجر عربي/إنجليزي متجاوب، بحث وفلاتر وفئات، تفاصيل منتجات وسلة.
- حساب عميل بالبريد وكلمة المرور على `/account`، مع تأكيد بريد واستعادة كلمة المرور عند ضبط إعدادات Supabase Auth وSMTP. Checkout للضيف يظل متاحًا.
- `GET /api/account/orders` يعيد آخر 50 طلبًا مرتبطًا بالمستخدم المصادق عليه فقط؛ لا يقبل معرّف مستخدم من العميل ولا يعيد الهاتف أو العنوان. Checkout المسجل يربط الطلب بـ`auth.users.id` المستخرج من جلسة موثقة خادميًا؛ الطلبات القديمة وطلبات الضيوف لا تُربط تلقائيًا بالحساب.
- Checkout يعيد التحقق من الأسعار والكميات والمخزون والخيارات قبل تسجيل الطلب.
- `GET /api/products` يعرض المنتجات المتاحة فقط عبر صفحات REST وحقول عامة محددة.
- `POST /api/checkout` يسجل الطلب بعد التحقق الخادمي؛ لا يجمع أموالًا ولا يتصل ببوابة دفع.
- `POST /api/discount/validate` يتحقق من كوبون الخصم والسلة؛ التحقق النهائي يُعاد داخل معاملة Checkout.
- `GET/POST /api/reviews` يعرض التقييمات المعتمدة ويستقبل تقييمات تنتظر موافقة الإدارة.
- `POST /api/track` يعرض حالة الطلب والإجمالي والمبلغ المدفوع واسمًا مخفيًا جزئيًا؛ يرسل الرمز في جسم الطلب لا في URL. الرمز مشفر ومتحقق منه بـAES-256-GCM، لا يكشف UUID الطلب، وتنتهي صلاحيته بعد 90 يومًا. لا تعيد الاستجابة الهاتف أو العنوان، وتستخدم `no-store`. صفحة `/order/track` تقبل الرمز يدويًا.
- `/api/admin/*` لإدارة المنتجات والطلبات والخصومات والإعدادات، مع عزل الشريك والتحقق من الجلسة.
- استيراد CSV للمنتجات يدعم حتى 100 صف في العملية ويرسل multipart إلى المسار الإداري الفعلي؛ الاستيراد ليس معاملة كلية، لذلك قد ينجح بعض الصفوف وتفشل أخرى مع عرض الأخطاء.

مصادقة العملاء بالبريد وكلمة المرور مضافة، ولا يوجد تسجيل دخول Google أو WhatsApp. تأكيد البريد واستعادة كلمة المرور يحتاجان SMTP موثوقًا وقائمة redirect مضبوطة في Supabase Auth؛ لا تعتبر إرسال البريد جاهزًا للإنتاج قبل تهيئة ذلك واختباره. تسجيل العملاء اختياري ولا يمنع Checkout للضيف. لا تظهر أزرار WhatsApp حتى يُضبط رقم عمل حقيقي ومعتمد في `NEXT_PUBLIC_WHATSAPP_NUMBER`.

## المتطلبات والتشغيل المحلي

- Node.js `>=22.13.0 <27` وnpm.
- مشروع Supabase مخصص للتطبيق عند استخدام Backend الحقيقي.

```bash
npm ci
cp .env.example .env.local
```

للتجربة المحلية المعزولة دون اتصال بـSupabase، اجعل `NEXT_PUBLIC_DEMO_MODE=true` في `.env.local` ثم شغّل:

```bash
npm run dev
```

افتح http://localhost:3000. حسابات Demo المحلية هي `Partner A` أو `Partner B` أو `Partner C`، وكلمة مرور العرض المحلي `aso-demo-2026`؛ لا تستخدمها في الإنتاج. بيانات المنتجات الاصطناعية متاحة في هذا الوضع المحلي فقط. تغييرات Demo تُحفظ تحت `.demo/` والصور في `public/demo/uploads/`؛ هذه الملفات مستثناة من Git، ووضع Demo غير مناسب لاستضافة متعددة النسخ.

## إعداد Supabase

يوضح `.env.example` أسماء المتغيرات المطلوبة. للإنتاج المحلي أو Vercel:

```dotenv
NEXT_PUBLIC_DEMO_MODE=false
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<publishable-key>
SUPABASE_SECRET_KEY=<server-only-secret-key>
ADMIN_SESSION_SECRET=<random-secret-at-least-32-characters>
# Optional independent key for encrypted order tracking; if omitted, a domain-separated key is derived from ADMIN_SESSION_SECRET.
ORDER_TRACKING_SECRET=
ADMIN_PASSWORD_PARTNER_A=<unique-long-random-password>
ADMIN_PASSWORD_PARTNER_B=<unique-long-random-password>
ADMIN_PASSWORD_PARTNER_C=<unique-long-random-password>
# Optional: verified business contact number, digits only
NEXT_PUBLIC_WHATSAPP_NUMBER=
```

أنشئ `ADMIN_SESSION_SECRET` عشوائيًا، مثلًا باستخدام `openssl rand -base64 48`، وضع كل الأسرار في مخزن أسرار محلي أو Vercel. `ORDER_TRACKING_SECRET` اختياري؛ عند تركه فارغًا يُشتق مفتاح تتبع مستقل وظيفيًا عن سر الجلسة، وتغيير السر يُبطل رموز التتبع السابقة. الرموز صالحة 90 يومًا. اجعل كلمات المرور قوية ومختلفة. لا تضف `.env.local` إلى Git، ولا تستخدم متغيرًا يبدأ بـ`NEXT_PUBLIC_` لأي مفتاح سري.

لتفعيل حسابات العملاء في Supabase Dashboard: فعّل Email provider، اشترط تأكيد البريد، عيّن Site URL إلى نطاق المتجر، وأضف مسار `/auth/callback` لنطاق Production وبيئات Preview المعتمدة إلى Redirect URLs. اضبط SMTP مخصصًا موثوقًا وإعدادات الرسائل قبل إطلاق التسجيل/الاستعادة؛ مزود البريد الافتراضي في مشروع Supabase ليس بديلًا لإعداد إرسال إنتاجي. يبقى تعطيل التسجيل في إعداد Supabase خيارًا آمنًا إلى أن يكتمل SMTP.

لتطبيق migrations من المستودع على مشروع Supabase المعتمد:

```bash
npx supabase login
npx supabase link --project-ref rtokjrupdvftacewvmxm
npx supabase db push
```

## النشر على Vercel

اربط مستودع `ahmed-abo-zahra/OSA-CLO` بمشروع Next.js على Vercel، واستخدم فرع `main` للنشر Production. اضبط متغيرات الإنتاج الموجودة في `.env.example` مع `NEXT_PUBLIC_DEMO_MODE=false`، وتأكد من وجود متغيرات كلمات المرور الثلاثة و`ADMIN_SESSION_SECRET` دون إضافتها إلى Git. اختبر Preview أولًا، ثم تحقق بعد النشر من الصفحة الرئيسية وصور الكتالوج و`/api/products` وتسجيل الدخول الإداري ورفض طلبات الإدارة غير المصرح بها.

لا تنشر ملف `.env`، ولا تطبع المفاتيح في سجلات CI أو الطرفية، ولا تستخدم بيانات Demo المحلية في الإنتاج. لا يوجد دفع إلكتروني؛ أي طلب يبقى غير مدفوع إلى أن يُتفق على آلية حقيقية خارج التطبيق.

## حدود النسخة الحالية

- كتالوج المنتجات الـ120 وصورها محتوى Portfolio/توضيحي محفوظ عمدًا للتقييم، وليس مخزونًا تجاريًا مؤكدًا.
- لا يوجد دفع إلكتروني؛ الطلبات غير مدفوعة حتى تأكيدها خارج التطبيق.
- حسابات العملاء بالبريد مدعومة في التطبيق، لكن تأكيد البريد/استعادة الحساب لا يعدان جاهزين للإنتاج حتى يكتمل SMTP وقائمة redirect واختبار الرسائل الحية في Supabase.
- Checkout للضيف متاح؛ الطلبات القديمة التي سُجلت قبل تسجيل العميل لا تُنسب تلقائيًا إلى حسابه.
- يلزم توفير سياسة خصوصية/شروط متجر معتمدة تجاريًا وقانونيًا قبل استقبال بيانات عملاء حقيقية؛ نص README ليس بديلًا عنها.
- لا تُنشأ طلبات أو تقييمات وهمية تلقائيًا؛ طلبات الاختبار يجب أن تستخدم بيانات اصطناعية وتُنظف بعد التحقق.
- لا تعتمد على قاعدة `.demo/` كقاعدة بيانات إنتاجية أو متعددة النسخ.
